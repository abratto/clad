# Experiment — build an app with CLAD (Expense Approvals)

> **Disposition.** The experimental app (`features/UC-01-submit-expense`,
> `features/UC-02-decide-expense`, `reference-impl/expense-micronaut`) was
> removed from the CLAD seed after the experiment to keep the seed small. This
> report preserves the findings and the verification evidence. Paths and
> commands below are historical; the platform fixes that came out of the
> experiment remain in the repository.

Goal: exercise the full CLAD loop with a deliberately non-trivial app, using
one sub-agent per stage and a human (the orchestrator) reviewing every gate.
Then run an iterative change and record the friction.

## App brief

**Expense Approvals** — a small internal HTTP service.

- Employees submit expense claims (amount, currency, category, description,
  receipt reference).
- Approvers decide claims (UC-02, not built in this experiment).
- Decisions must respect a per-category budget seeded by Finance.
- State is durable in PostgreSQL; the schema is generated by Python Rmap.
- Every state change is a concept action with a flow token (auditable).

### Actors

- **Employee** — submits claims and needs to know their status.
- **Approver** — reviews pending claims and decides within budget.
- **Finance Admin** — maintains category budgets (out of scope for v1).

### Confirmed goals (v1)

| Actor | Goal | Priority | In scope |
|---|---|---|---|
| Employee | Submit an expense claim | P0 | yes |
| Approver | Decide an expense claim | P0 | yes |

Out of scope (v1): configure budgets, reimburse/pay, receipt OCR, FX,
authentication/SSO (adapter assumed), reporting/export, notifications,
dedicated status tracking.

## What was actually built

- **Stage 00:** `features/_system/stages/00_actor-goal/output/actors.md` and
  `goals.md` (2 in-scope goals; Gate 0 approved after one boundary correction).
- **UC-01 `submit-expense`:** full pipeline, stages 01 → 05.
  - Concepts: `ClaimIntake` (`validate` pure guard, `submit` write, 8 facts)
    and `ClaimPolicy` (`checkCategory`, `checkCurrency`, seeded policy).
  - 18-row chain (success + 2a–2f refusals), 11 declarative syncs.
  - Stage 03b CSDP models; Rmap `V1__expense_rmap.sql` + `rmap-schema.json`
    (`claim_intake` keyed by `claim_id`; `claim_policy__category`,
    `claim_policy__currency_rule`).
  - Contracts, frozen Acceptance Spec, 7 native HTTP flow tests.
  - Java 21 + Micronaut module `reference-impl/expense-micronaut`
    (in-memory and Postgres storage wiring, debug surface, seeded policy).
  - `mvn ... expense-micronaut -am test`: **31 tests, 0 failures**.
  - Stage 05 live smoke + captured `/api/dev/flow` evidence; feature closed
    (`Current stage: None — feature complete`).
- **Iteration A — bug fix `reject-missing-employee`:** a blank/missing
  `X-Employee-Id` created a claim with an empty owner. Re-entry at Stage 01
  (use case extension 2f), 01b (new `REFUSED_EMPLOYEE` branch), 02, 03, 04b,
  04c, 04d, 04e, 05. 7/7 flow tests green; change content-bound approved and
  closed.
- **Iteration B — feature change `add-claim-tags`:** optional claim labels,
  added as a new `ClaimTagging` concept (`tags: ClaimId -> Tag -- zero or
  more`) rather than changing `ClaimIntake`. Re-entry at Stage 01 → 05; Rmap
  regenerated V1 in place (app not deployed) adding the
  `claim_tagging__tags` child table `(claim_id, tags)`; 12 syncs; the success
  flow is now submit → validate → policy checks → submit → tag → respond.
  Flow tests green (submit with tags persists both labels; no tags writes
  none); a Docker Postgres test now asserts the tag rows. Change
  content-bound approved and closed.
- **UC-02 `decide-expense`:** full pipeline, stages 01 → 05.
  - Reuses/extends `ClaimIntake` (`lookup`, `close`; no state change) and
    introduces `ClaimDecision` (decision record) and `SpendBudget`
    (compound `(Category, Currency)` budget).
  - 29-row chain with joins; 18 declarative sync rules; route
    `claims/{claimId}/decision` (distinct from UC-01's `claims`).
  - V2 Rmap migration: `claim_decision` keyed by `claim_id`, and
    `spend_budget__category_and_currency` with a compound key.
  - Frozen Acceptance Spec with 9 native flow tests; budgets seeded per
    (category, currency).
  - Runtime descriptor merge: the app loads UC-01 and UC-02 descriptors and
    concatenates their models; a Docker-gated Postgres test proves the
    merged schema + `RmapPostgresFactStore` end-to-end.
  - `mvn ... expense-micronaut -am test`: **75 tests, 0 failures**
    (16 HTTP flow tests: 7 submit + 9 decide). Postgres: 2 additional
    persistence/flow tests.

## Friction log

Status: **fixed** = changed in the CLAD seed during the experiment;
**open** = remains to address.

| # | Stage / surface | Observation | Status |
|---|---|---|---|
| 1 | project gate `verify_model_current` | A freshly bootstrapped feature has an empty `03b/output/.gitkeep`; the gate treated it as a model set and failed every new UC with `no .data-model.md files found`. Now skipped until a model exists; regression test added. | fixed |
| 2 | `generate_data_model._identifying_type` | An `…Id` subject was identified by the first `…Id`-valued fact (`ClaimId` → `EmployeeId`), so Rmap keyed `claim_intake` by `employee_id` and dropped `claim_id`. Now identifier subjects identify themselves; non-identifier entities use a `-- unique` identifying fact. Regression test added. | fixed |
| 3 | `advance` / `verify_artefacts` stage routing | A satisfied no-op 04a (`storage.persistent=false`) routed past a pending Gate 2, so Gate 2 could never be presented. Routing now clamps at the last unapproved gate; regression test added. | fixed |
| 4 | `verify_concept_novelty` after Gate-2 promotion | Promotion puts the feature's own concepts in the catalog, and the Gate-1 novelty gate then demanded `## Why not existing` against itself. Own introductions (`introduced-by`/`extended-by` = this feature) are now excluded; regression test added. | fixed |
| 5 | Stage 01b/02 design | R23 (refusal before any write) forced a pure `ClaimIntake.validate` guard plus policy checks; the first map/chain drafts tried to make `submit` refuse. Human review caught it; the stage contract does state R23, but the first drafts missed it. | process |
| 6 | `generate_syncs` on branches | Response field name collision: the chain's body `status: "PENDING"` collides with `Web.respond`'s transport `status`, so the generator uses `claimStatus` while the contract returns `status`. The controller maps it, but the naming is a latent ambiguity. | open |
| 7 | `generate_syncs` iterative re-run | `--write` overwrites all resolved syncs and renumbers matrix row ids. **Fixed follow-up:** `--update` keeps same-stem resolved syncs, patches row ids, and deletes stale files; changed transitions still need re-resolution. | fixed (partial) |
| 8 | `generate_syncs` TODO scaffolding | Downstream syncs had no scaffold for request-originated binds; the agent had to author `requested.*`/`SiblingInput` binds and terminal message/claimId args by hand. The TODO wording ("no function call") also makes the engine's `triggerInput`/`triggerField` constructors look illegal. | open |
| 9 | `generate_data_model` TODO coverage | Reference schemes are generated silently and are not a `<TODO: judgment>` marker, so the generator bug in #2 passed the fidelity check (fidelity ignores `object-type` lines). Value constraints from action pre/postconditions have no hint in the skeleton. | open |
| 10 | 04a Rmap | `relational_mapping` reports `[skip] inputs not present: …/output` for a persistent profile whose real output is the generated migration/descriptor — misleading. `Instant` and `Boolean` fall through to `TEXT`/`varchar`; `Int` is `INTEGER`. | open |
| 11 | 04c `generate_acceptance_spec` | It concatenated every chain row into one expected token chain, unusable; postconditions truncated at line wraps. **Fixed follow-up:** per-branch paths via `chain_paths.py`; full wrapped postconditions. | fixed |
| 12 | 04c greenfield scaffold | The stage contract requires a compiling boundary scaffold, but the first pass authored only tests/spec; the module pom/controller/DTOs were missing. A follow-up scaffold was needed. | process |
| 13 | 05 debug surface | `/api/dev/flows` listed only in-flight ids; completed flows were unlistable. **Fixed follow-up:** `/api/dev/archive` in `DebugApi` + both debug controllers; capture falls back to it. | fixed |
| 14 | 05 archive buffer | Capacity 100 with silent eviction; firing 150 requests before fetching evicted the first 50 (including the success flow). | open |
| 15 | 05 `capture_observations --flows-dir` | Parsed every `*.json` as a scenario; helper/observations files became bogus scenarios. **Fixed follow-up:** only payloads with an `actions` list (or a flow wrapper) are captures. | fixed |
| 16 | 05 `generate_trace` | Derived the expected chain from every row, so a multi-branch scenario could never match one flow. **Fixed follow-up:** per-branch sections from `chain_paths.py`. | fixed |
| 17 | Mutation gate | `mutation.command` targets `java-legible`, not `expense-micronaut`; the 04d/04e mutation check skips, so the new module has no mutation score. Project-scoped mutation config is a gap for multi-module apps. | open |
| 18 | Iterative change + gates | Editing 01b/02/03/04b/04c stales Gate 1/2/3 and forced per-stage re-approval mid-change. **Fixed follow-up:** `advance` defers gates under `CLAD_CHANGE_RUN`, `change approve` re-baselines affected gates, and `change plan` derives from the impact matrix. | fixed |
| 19 | Iterative change planning | The first change record set earliest re-entry to 01b; review found the use-case pre-condition needed extension 2f, so the true earliest was 01. `change plan` could not derive it (nothing changed yet / diff unreliable on an untracked feature). | process |
| 20 | Iterative change diff | `change review` showed `Diff summary: (none)` because the feature folder is untracked in the experiment tree; the content hash still binds. A real project with committed features would show the diff. | experiment |
| 21 | Stage 05 close | `advance` closed RESUME to `None — feature complete`; starting a change on a closed feature works, but the active-feature heuristic then relies on `_changes`. | open |
| 22 | Branch/commit rules | AGENTS §2.7 requires a pushed feature branch before Stage 01 and a commit per gate; the experiment was explicitly no-commit/no-push, so those rules were not exercised. The dirty tree also made `git diff`-based planning unreliable. | experiment |
| 23 | `artifact_parsers.parse_state_relations` | Compound subjects `(Category, Currency)` were dropped, so `SpendBudget` parsed as stateless and 03b/Rmap would lose its facts. Character class widened; regression test added. | fixed |
| 24 | Route parsing / cross-UC collision | `POST /claims/{claimId}/decision` was truncated to route `claims`, so UC-01 and UC-02 shared the same bootstrap route and fired each other's rules. Fixed in `generate_syncs._root_route_method` and `verify_sync_flow_pin.route_of` (full path, path params preserved); UC-01's Java rule also gained its declared `route="claims"` matcher. Regressions added. | fixed |
| 25 | Brace-blind parsers | The `{claimId}` route also broke `generate_shared_triggers`/`verify_sync_then_shape` (regex stopped at `}`/treated `{claimId}` as a body frame). Fixed with brace-balanced/quoted-literal-safe extraction. | fixed |
| 26 | Canonical promotion after an iterative change | The approved change updated the proposal/contract but not the canonical spec; `verify_concept_corpus_current` checks history, not content. **Fixed follow-up:** `approve_gate --iterative` promotes current proposals when Gate 2 is re-baselined. | fixed |
| 27 | Multi-feature Rmap / descriptor | Rmap emits one migration + descriptor per feature. UC-02's tables went into a V2 migration, but the runtime needed a merged descriptor; the app's `ExpenseSchemas` concatenates the two JSON descriptors. A project-level Rmap aggregate (or a first-class descriptor merge) is missing. | open |
| 28 | Iterative schema changes | Rmap renders the full schema for the feature's models, not an ALTER diff. UC-02 added only new tables so V2 worked; a state change to an existing concept (new column) would need a hand-authored ALTER or a diff mode. | open |
| 29 | Postgres seed helpers | Seeding two mandatory facts on one row outside an engine action produced a half-written row and a NOT NULL failure on Postgres. Seed helpers now buffer via `TransactionalRegion.beginAction/flushAction`; a general concept/test seeding convention would help. | fixed (app) |
| 30 | Shared-trigger view | The view is route-blind (keyed by concept.action+outcome), so UC-01 and UC-02 both appear in one `Web.request/Routed` row; the route distinction exists only in the packs/flow-pin checks. Add a Route column/key. | open |
| 31 | Acceptance binding vs persistence tests | Any test class named `*FlowTest` must be documented in the Acceptance Spec; a Docker-gated Postgres persistence test initially tripped this. Renamed to `*PersistenceTest` (the check is name-based, not role-based). | open |
| 32 | Gate reopening during a change | A structural change needs Gate 2 re-approved for new content, but there was no sanctioned "reopen gate" command. **Fixed follow-up:** `./clad approve --reopen N` / `./clad reopen N`; the registry treats an active change's proposals as in-flight. | fixed |
| 33 | Promotion receipt overwrite | Re-promoting a feature rewrote `_promotions/<feature>.md` with only the concepts promoted in that run, dropping earlier ones; `verify_concept_corpus_current` then failed. Receipts now merge prior concepts + canonical history, and a stale receipt forces a rebuild instead of a no-op. | fixed |
| 34 | Cross-feature canonical ownership | After UC-02 extended `ClaimIntake`, UC-01 can no longer re-promote it (correctly refused: "the corpus must not move backwards"). A feature that introduces a concept loses promotion ownership once another feature extends it; changes to that concept must be promoted from the current owner. | open |
| 35 | Shared implementation parity across UCs | Changing UC-01's sync set forced a rename of a class in the shared `expense-micronaut` sync directory to keep UC-02's `implementation_parity` green — a cross-feature implementation coupling not represented in either UC's artefacts. | open |
| 36 | Feature-change gate churn | A feature change re-staled Gates 1/2/3 and required per-stage re-approval plus a final change approval. **Fixed follow-up:** one `change approve` now re-baselines the affected gates; `change review` lists them. | fixed |

## Follow-up implementation (P0/P1)

Implemented after the experiment, with regressions:

- **Gate churn:** `verify_stage_sequence --defer-gates` (used by `advance` and
  `verify_artefacts` under `CLAD_CHANGE_RUN`); `approve_gate --iterative`
  re-baselines every gate whose stage hashes changed; `--reopen` plus
  `./clad reopen <N>` / `./clad approve --reopen <N>`; `change plan` derives
  affected stages from the impact matrix (not `git diff`); `change review`
  lists stale gates; `present_gate` adds one-line artefact descriptions;
  `advance` prints all `[FAIL]` blocks instead of the last 25 lines.
- **In-flight proposals:** `verify_concept_corpus.rule_registry` treats a new
  proposal on an active change as a warning, not a failure.
- **Promotion on change:** `approve_gate --iterative` promotes the current
  proposals when the change re-baselines Gate 2.
- **Sync generation:** `generate_syncs --update` preserves unchanged resolved
  syncs, patches their row ids, and deletes stale sync files.
- **Acceptance/trace generation:** `chain_paths.py` enumerates root-to-terminal
  branches; both generators emit a main scenario plus per-branch sub-cases with
  correct token chains; postconditions keep wrapped lines.
- **Debug capture:** `/api/dev/archive` lists retained completed flows (engine
  `DebugApi` + both controllers); `capture_observations` falls back to it and
  ignores non-flow JSON in `--flows-dir`; `/api/dev/archive-info` exposes
  retention/eviction.
- **Project Rmap:** `rmap --features-dir` aggregates the canonical corpus into
  one descriptor; `--baseline <path>` + `--alter` emits incremental
  CREATE/ALTER DDL (mandatory columns without defaults refused; drops
  reported, not emitted); `--force` guards an applied base migration.
- **Typing and grammar:** `Instant` → `TIMESTAMP`, `Boolean` → `BOOLEAN` (Java
  store coercion); the feature responses use `httpStatus` for the transport
  (domain fields such as `claimStatus` stay distinct), and
  `verify_sync_then_shape` rejects legacy `status:`, missing `httpStatus`,
  duplicates, and non-numeric codes; acceptance binding is role-based
  (`flows/`); shared-trigger view has a Route column; `generate_syncs --update`
  warns on orphaned Java classes; `verify_trace_complete` checks `###`
  sub-cases; `--defer-gates` requires an active change; the
  `relational_mapping` skip names the generated artefacts.
- **Rmap baseline discovery:** `--record-baseline` records a deployed
  descriptor; `--alter` finds it from `--baseline NAME`, `rmap.baseline`, or
  `_generated/rmap-baselines/default.json`.
- **Mutation:** `scripts/mutation-score-expense.sh` runs PIT over the expense
  concepts/syncs; **83.7%** against the 80% threshold (feature-local
  `mutation.command`).
- **Shims:** the old `verify_*` scripts are retained as deprecated CLI
  wrappers for one minor; the grouped families are authoritative.

Tests added: gate reopen/defer/reconcile, change plan, registry active-change,
sync `--update`, chain paths, branch acceptance/trace, debug archive, capture
archive fallback. Suite: **505 passed** at this point.

## Recommended next steps

1. **Hygiene:** complete any remaining task-4 docs and defer task 2
   (non-relational storage) until a real consumer exists.
2. **Longer-term:** retire the deprecated `verify_*` shims in a future major
   once external references are gone; extend the baseline registry to
   per-environment automatic naming if the app deploys to multiple
   environments.
